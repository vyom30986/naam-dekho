# Static SEO pages

Naam Dekho publishes 697 static HTML files under `frontend-jsx/public/`. They
are generated by one script in the backend, they are not part of the React
app, and they are the reason the domain has anything for a search engine to
index. This document explains what they are, how they are built, and what will
break them.

Read the warning below before you run any build command.

---

## Read this first: build:names needs the database

> **`npm run build:names` regenerates all 697 files. If it cannot reach the
> database, it silently falls back to a built-in 50 name corpus, writes about
> 50 pages, and rewrites `sitemap.xml` to match. The 697 pages are gone.**
>
> The repo is not under version control, so there is no `git checkout` to undo
> it. Recovery means restoring the database, or a dump of it, and running the
> command again.

The fallback lives in `backend/src/scripts/name-corpus.ts` (exactly 50 entries)
and it is deliberate: it lets a fresh clone or CI run the build with no
infrastructure. It is not a safety net for a real build.

Two conditions trigger it, both in `loadCorpus()` in
`backend/src/scripts/build-name-pages.ts`:

| Condition | What happens | Console line begins |
|---|---|---|
| `stackHealth().db` is false | Fallback corpus used | `No database` |
| `corpus_names` returns zero published rows | Fallback corpus used | `corpus_names is empty` |

Both lines end with the words "using the built-in fallback corpus".

Those warnings are the only signal. The build then reports success and exits 0.

One detail worth knowing. `stackHealth()` in `backend/src/lib/devstack.ts`
only probes when `NODE_ENV` is `development`. Outside development it returns
"all healthy" without checking, so the build goes straight to the query and a
missing database surfaces as a thrown connection error instead of a quiet
fallback. `NODE_ENV` is currently `development`, which is the quiet case.

**Before running the command, confirm the corpus is really there:**

```sql
select count(*) from corpus_names where published = true;
```

Expect 536. If you get 0, or the query fails, do not run the build.

Nothing on these pages is authored by hand, so no content is lost when this
goes wrong. Everything is derived from `corpus_names` plus deterministic
TypeScript. The database is the asset; the 697 files are output.

## What these pages are

Two kinds of content live here.

**Name pages.** One page per published name, at `/n/aarav.html` and so on.
Each one carries the name across ten Indian scripts, its Chaldean compound and
root number with the ruling planet, the nakshatra and rashi its first syllable
maps to under the Avakahada chakra, its natural short forms, and a
pronunciation reading. All of it is computed by the same engines the live
product runs on. None of it exists in a public dataset a competitor could copy,
which is the whole argument for these pages ranking rather than being demoted.

**Keyword clusters.** The name pages answer "what does Aarav mean". The
clusters answer the question space around it: the nakshatra a family was given
at the naming ceremony, the numerology root, the domain ending, the trademark
class, the script a name is written in.

### Why static HTML and not React routes

A file that already contains its content in the markup gets indexed reliably.
A client-rendered route is a gamble on whether the crawler executes the
JavaScript, and how soon. These files also cost nothing to serve, and they
cannot break when the app changes.

They deliberately do not use the React app's `index.css`. That stylesheet
follows the reader's theme; these pages carry their own CSS inline and render
identically for everyone. There is no stylesheet request, no build step, and
nothing that can fail between a crawler and the words.

### Unlinked, but not cloaked

These pages are not linked from the app's navigation. A customer using the
product never lands in them. Verified: nothing under `frontend-jsx/src/` links
to `/explore/`, `/n/`, `/nakshatra/`, `/names/` or `/trademark-class/`. The
links run the other way, from the static pages back into the app.

They serve byte identical content to every visitor. There is no crawler
detection anywhere in `backend/src/seo/`, no user-agent branch, no hidden text,
no content swapped in after load. That is cloaking, and it is the one SEO
technique that reliably gets a domain removed from the index. If you are ever
tempted to "improve" one of these pages by showing crawlers something the
reader does not get, do not.

The `/names/` 39 breaks down as 12 letter pages, 9 boys' pages, 7 girls'
pages, 10 meaning themes and 1 index.

Two conventions that look like mistakes and are not:

- **Script pages are filed under a language, not a script code.** The file is
  `/script/punjabi.html`, not `/script/gurmukhi.html` or `/script/pa.html`,
  because "write my name in Punjabi" is the query people type. There are nine
  script pages, not ten, because Hindi and Marathi share Devanagari and share
  one page, filed under `hindi.html`.
- **There is no second trademark hub.** `seo/trademark.ts` emits
  `/trademark-class/index.html` itself and `seo/hub.ts` deliberately does not,
  because two `SeoDoc`s on the same path would make whichever the build writes
  last the winner. The same applies to `/numerology/index.html`, owned by
  `seo/numerology.ts`.

## How the build works

One command, run from `backend/`:

```bash
npm run build:names
```

That is `tsx src/scripts/build-name-pages.ts`. The output directory is
resolved as `../frontend-jsx/public` relative to the **current working
directory**, so running it from the repo root writes outside the repo. Always
run it from `backend/`.

What the script does, in order:

| Step | What it does |
|---|---|
| 1 | `loadCorpus()` reads published rows from `corpus_names`, drops any meaning that is not `verified`, sorts by name. Falls back to the 50 name list if the database is unreachable or empty. |
| 2 | `registerNameSpellings()` teaches the transliterator every verified `native_spelling` in the corpus, before anything renders. |
| 3 | Writes one name page per corpus entry, then `/n/index.html`. |
| 4 | Calls the nine cluster builders with a single `SeoCtx`, collecting their `SeoDoc[]`. |
| 5 | Scans the collected HTML for internal links to pages nobody emitted, and remembers them. |
| 6 | Writes every cluster document, creating directories as needed. |
| 7 | Writes `sitemap.xml`: 9 static routes, one URL per corpus name, one per cluster document. |
| 8 | Writes `robots.txt`. |
| 9 | Prints a per-cluster summary, the dangling link warning if any, and the origin it used. |

### Step 2 matters more than it looks

Every Indian script on the site is derived from the Devanagari. Roman spelling
does not record vowel length, so a name transliterated blind becomes रम rather
than राम unless the lexicon has the real spelling. `registerNameSpellings()` in
`backend/src/lib/transliterate.ts` supplies it. 210 of 536 names carry a
verified `native_spelling`; the remaining 326 fall back to transliteration,
which is wrong for roughly 63% of names.

One wrong vowel here is wrong in all ten scripts, on every name page, in every
cluster that prints a script, and on the certificate. The same function is
called at server start in `src/server.ts`.

A trap: the build assigns the return value to a `const taught` that is never
used afterwards. It looks like dead code and it is not. Deleting the call
because the variable is unused would silently degrade every script on every
page. Remove the variable if it bothers you, keep the call.

### The corpus the builders see

`SeoCtx.corpus` is not the raw table. It is published rows only, with any
unverified meaning stripped out, sorted alphabetically. A page renders without
a meaning rather than with a guess, which is the same rule the live product
follows. Of the 536 published names, 260 carry a verified meaning that these
pages may print. 259 more have an unverified Gemini proposal held back in the
console's review queue at `/admin/corpus`, and 17 have nothing.

## The cluster contract

Everything in `backend/src/seo/` implements one contract, defined in
`backend/src/seo/shell.ts`. The build script never learns what a cluster is.
It calls a function, gets finished documents back, and writes files.

**Input, `SeoCtx`:**

| Field | Type | Notes |
|---|---|---|
| `siteOrigin` | `string` | From `SITE_ORIGIN`, default `https://naamdekho.net`, trailing slash stripped |
| `corpus` | `Array<{ name, gender?, origin?, meaning? }>` | Published, filtered, sorted. `meaning` is present only when verified. |

That is the whole input. A builder is handed the corpus and nothing else, which
is why cross-cluster link checks have to be recomputed rather than imported
(see below).

**Output, `SeoDoc[]`:**

| Field | Type | Notes |
|---|---|---|
| `path` | `string` | Absolute site path including `.html`, for example `/nakshatra/krittika.html` |
| `html` | `string` | The complete document |
| `priority` | `string` | Sitemap priority, `"0.0"` to `"1.0"` |
| `changefreq` | `"daily" \| "weekly" \| "monthly" \| "yearly"` | Sitemap changefreq |

Current convention: `0.8` for a cluster's main pages, `0.7` for its hub, `0.6`
for `/explore/`, `0.7` for name pages, all `monthly`.

**The page shell, `renderSeoPage()`**, takes a `SeoPage` (title, metaDesc,
path, siteOrigin, crumbs, optional jsonLd, body) and returns the finished
document. It supplies:

- `<!doctype html>`, `lang="en-IN"`, viewport, title, meta description
- canonical URL, Open Graph tags, `twitter:card summary`, the favicon link
- the Google Fonts stylesheet link
- your JSON-LD objects, plus a `BreadcrumbList` generated from the same
  `crumbs` array that renders the visible breadcrumb, so the two cannot
  disagree
- `PAGE_CSS` and `CLUSTER_CSS` inline
- the site header (logo, "How it works", "Pricing"), the breadcrumb line, your
  body, and the footer

Typefaces load from `fonts.googleapis.com` in the reader's browser. If that
request fails the page still renders, in the fallback stack declared in the
CSS. Nothing else is fetched from anywhere.

Also exported and worth using rather than reinventing: `esc()` for HTML
escaping, `seoSlug()` for the lowercase hyphenated ASCII slug every SEO URL
uses, and `ctaBlock()` for the closing call to action every cluster page ends
with.

## Adding a new cluster

The design goal was that a cluster is one file plus one line. It holds.

1. **Create `backend/src/seo/<cluster>.ts`** exporting one function with the
   signature `build<Cluster>Pages(ctx: SeoCtx): SeoDoc[]`.
2. **Decide the publish threshold before you write the template**, and write
   the reasoning into the file as a comment. Every existing cluster does this.
   The question to answer is: with a thin corpus, is this page still worth
   landing on, or is it the template with a variable swapped in.
3. **Build each page body as an HTML string** and pass it to `renderSeoPage()`
   with a title, meta description, path, `ctx.siteOrigin`, breadcrumbs and any
   JSON-LD. Use `esc()` on anything that came from data. Use the classes
   already in `PAGE_CSS` and `CLUSTER_CSS` so the cluster does not look like a
   different site.
4. **Return `SeoDoc[]`.** Paths must start with `/` and end with `.html`. The
   writer creates directories recursively, so a new folder needs no setup.
   Return an empty array when the threshold is met by nothing; the build
   handles a cluster that emits zero pages.
5. **Register it in `backend/src/scripts/build-name-pages.ts`**: one import,
   and one entry in the `CLUSTERS` array, for example
   `{ name: "festivals", docs: buildFestivalPages(seoCtx) }`. The console
   summary, the file writing and the sitemap all pick it up from there.
6. **If your pages link to another cluster,** copy that cluster's threshold
   constant into your file and apply it before emitting the link, and add your
   file to the mirrored list in the header of `backend/src/seo/hub.ts`. See the
   next section for why this is copied rather than imported.
7. **Decide whether it needs an inbound entry point.** A cluster that only
   links to itself is a set of orphans. Either emit your own index, as
   `numerology.ts` and `trademark.ts` do, or add it to `seo/hub.ts` so
   `/explore/` and a cluster index link into it. If you add a hub page, do not
   emit a second document on a path another builder already owns.
8. **Typecheck, then build with the database up.** `npx tsc -p tsconfig.json`
   in `backend/` compiles clean today, so any error is yours.
   (`npm run lint` in `backend/` does not work: the script exists but eslint is
   not installed there.) Then run `npm run build:names` and read the summary:
   the new cluster's count, and whether the dangling link warning appeared.

## Minimum content thresholds

Every cluster has a rule that decides which pages it is allowed to emit. The
rules exist for one reason. Publishing a set of near-identical pages that
differ only in a heading and a couple of numbers is the doorway pattern that
gets a site demoted, and a demotion lands on the whole domain, including the
537 name pages that earn their keep. The second reason is honesty: a page
titled "Vishakha nakshatra baby names" that lists no names has promised
something it does not contain.

| Cluster | File | Rule | Value | Effect today |
|---|---|---|---|---|
| Nakshatra | `nakshatra.ts` | Corpus names beginning with one of the star's four pada syllables | `MIN_NAMES = 1` | 25 of 27 stars publish. Vishakha and Uttara Bhadrapada match no published name. |
| Rashi | `rashi.ts` | Corpus names under the sign | `MIN_CORPUS_NAMES = 6` | All 12 publish |
| Numerology | `numerology.ts` | Corpus names whose Chaldean root is that number | `MIN_CORPUS_NAMES = 5` | All 9 publish |
| Letters | `letters.ts` | Corpus names starting with the letter | `MIN_NAMES = 12` | 12 letters publish. Q, X, Z, W and usually F drop out, which is the intended outcome. |
| Letters, gendered | `letters.ts` | Applied independently to each gendered subset | `MIN_GENDER_NAMES = 12` | 9 boys' pages, 7 girls' pages |
| Letters, gendered | `letters.ts` | Subset suppressed when it is most of its parent | `GENDER_DUPLICATE_SHARE = 0.8` | Stops a gendered page being the letter page with a different `<h1>` |
| Meanings | `meanings.ts` | Corpus names sharing the theme | `MIN_NAMES = 6` | 10 themes publish |
| Meanings | `meanings.ts` | Smaller theme yields when it is mostly inside a larger one | `MAX_SUBSET_SHARE = 0.8` | Stops two URLs competing with the same list |
| Scripts | `scripts.ts` | Corpus names that actually **render** in that script | `MIN_NAMES = 25` | 9 script pages |
| Domains | `domains.ts` | Completeness, not count: a priced row in `TLDS` plus 2 audiences it suits, 2 it does not, 2 paragraphs, 1 specific question | `isPublishable()` | All 14 endings clear it |
| Trademark | `trademark.ts` | Completeness, not count: plain-English scope, 4 example businesses, 2 exclusions with the right class, 2 companion classes with reasons, 1 specific question | `isPublishable()` | All 45 classes clear it |
| Hub | `hub.ts` | Emits a cluster index only when that cluster has at least one page, and `/explore/` only when at least one index exists | guards in `buildHubPages()` | 6 pages |

Two clusters use a completeness test rather than a count because no corpus
feeds them. All 45 Nice classes exist whether or not anyone has thought about
them, and adding a fifteenth TLD is a one-line edit. If either of those alone
minted a page, the page would be a heading over shared tables.

### They recompute every build

No threshold is remembered anywhere. There is no "published" flag on a
nakshatra or a letter. Every builder recounts on every run, so:

- a page publishes itself the moment the corpus reaches its bar, and
- a page withdraws itself if a corpus edit takes it below.

This is the mechanism the whole cluster system rides on. As the 259 pending
meaning proposals are approved in `/admin/corpus`, the meaning themes thicken
and new theme pages appear with nobody editing a threshold. If you find
yourself adding a manual publish list, you have removed the feature.

Note when reading `meanings.ts`: the threshold comment opens by arguing for
`MIN_NAMES = 10`, then a dated note at the bottom of the same block records
the lowering to 6, with the measured page counts at 10, 8, 6, 5 and 4. Read
the whole block. The constant is 6.

The rationale comments also refer to numbered rules ("RULE 2", "rule 4") from
an SEO brief that is not in this repo. Unverified where that brief lives. Each
file restates its own reasoning in full, so nothing is missing from the code.

### Row caps are not thresholds

Separate from the publish rules, most clusters cap how many rows one table may
carry: `MAX_ROWS_PER_PADA = 40`, `MAX_NAME_ROWS = 60`, `MAX_ROWS = 120` on the
script pages, and so on. Nothing is orphaned past a cap, because every name has
its own `/n/` page and `/n/index.html` lists all of them. The overflow note on
the page points there rather than paginating.

## The dangling link check

A hub linking to a page nobody emitted is an internal 404, arriving from your
own sitemap. That is worse than a missing link, and it surfaces in Search
Console weeks later.

So after the builders run and before anything is written, the build collects
every emitted path, scans every cluster document for `href="/....html"`, and
reports any target that was not emitted. Links into `/n/` are excluded, since
a name page exists for every corpus name by construction.

The warning looks like this:

```
  3 internal links point at pages that were not emitted:
    /names/starting-with-q.html
    ...
```

Under the list the build prints two more lines: that a cluster is linking into
another cluster past its threshold, and a hint for finding the file that does
it, `grep -rl "<path>" ../frontend-jsx/public`.

**What it means:** one cluster linked to another cluster's page without
applying that cluster's publish rule, so the link points at a page the build
skipped. It is a warning, not an error. The build still writes the files and
exits 0. Fix it before deploying.

The printed hint assumes a Unix shell. On Windows PowerShell, `Select-String`
over `frontend-jsx\public` is the equivalent.

**Why the mismatch happens at all.** A builder receives only `SeoCtx`, so the
only way to know whether `/names/starting-with-q.html` will exist in this build
is to apply the rule that decides it. Those rules are therefore copied between
files rather than imported, on the reasoning that one cluster's threshold
change should not silently break another cluster's links. The cost is that a
threshold change has to be made in several files.

The mirrored copies, with the header of `backend/src/seo/hub.ts` as the
register of them:

| Constant | Where copied | Value there | Source of truth |
|---|---|---|---|
| `NAK_MIN_NAMES` | `scripts.ts` | 1 | `nakshatra.ts` `MIN_NAMES = 1` |
| `NAKSHATRA_MIN_NAMES` | `rashi.ts` | 1 | `nakshatra.ts` `MIN_NAMES = 1` |
| `NAK_MIN_NAMES` | `numerology.ts` | **8** | `nakshatra.ts` `MIN_NAMES = 1`. Drifted. |
| `LETTER_PAGE_MIN_NAMES` | `meanings.ts` | 12 | `letters.ts` `MIN_NAMES = 12` |
| `NUMBER_PAGE_MIN_NAMES` | `meanings.ts` | 5 | `numerology.ts` `MIN_CORPUS_NAMES = 5` |
| `LETTER_MIN_NAMES`, `LETTER_MIN_GENDER_NAMES`, `THEME_MIN_NAMES`, `NAK_MIN_NAMES`, `RASHI_MIN_NAMES`, `NUMBER_MIN_NAMES`, `SCRIPT_MIN_NAMES` | `hub.ts` | 12, 12, 6, 1, 6, 5, 25 | The respective cluster files |

The `numerology.ts` copy is stale: it says 8 where `nakshatra.ts` now says 1.
The drift is in the safe direction and the file's own comment anticipates it.
The numerology pages link to fewer star pages than exist, which costs internal
links; the opposite drift would put a 404 on nine pages. Worth fixing, not
urgent. Do not "fix" it by importing the constant across cluster files, which
is the thing this design is avoiding.

## sitemap.xml and robots.txt

Both are generated by `build:names` and written into `frontend-jsx/public/`.
**Any manual edit to either file is overwritten by the next build.** Change the
script, not the file.

**`sitemap.xml`**, currently 705 URLs:

| Group | Count | Priority | changefreq |
|---|---|---|---|
| React routes: `/`, `/how-it-works`, `/pricing`, `/n/`, `/privacy`, `/terms`, `/cookies`, `/cancellation-refund`, `/payment-terms` | 9 | 1.0 for `/`, 0.9 for `/n/`, 0.8 for the two marketing pages, 0.3 for the legal pages | weekly to yearly |
| Name pages | 536 | 0.7 | monthly |
| Cluster documents | 160 | as each `SeoDoc` declares | as each `SeoDoc` declares |

697 files against 705 URLs reconciles like this: the 9 React routes include
`/n/`, which is the file `/n/index.html`, and the other 8 have no file of their
own. `lastmod` is the build date for every URL; there is no per-page change
tracking.

**`robots.txt`**:

```
# Naam Dekho
User-agent: *
Disallow: /account
Disallow: /sign-in
Disallow: /admin
Allow: /

Sitemap: https://naamdekho.net/sitemap.xml
```

The `Allow: /` sitting after the three `Disallow` lines does not cancel them.
Google and Bing apply the most specific matching rule, so `/admin` stays
blocked. The disallow list is the `DISALLOWED` array in the build script.

Note that the sitemap line carries `SITE_ORIGIN`, so it points wherever the
last build pointed.

## Deployment

The pages sit in `frontend-jsx/public/`. Vite copies `public/` into `dist/`
verbatim, so they ship with the normal frontend build and are served as files
by whatever serves `dist/`. There is no server route to configure.

Sequence for a production deploy:

1. Set `SITE_ORIGIN` in `backend/.env` to the live origin. Canonical URLs, Open
   Graph URLs, JSON-LD items and every `<loc>` in the sitemap are absolute and
   baked in at build time. A build run with the default leaves the wrong origin
   in 697 files.
2. Confirm the database is reachable and `corpus_names` has its published rows.
   See the warning at the top of this document.
3. From `backend/`: `npm run build:names`. Read the summary. The cluster counts
   should look like the table above, and the dangling link warning should not
   appear.
4. Build the frontend. Note that `npm run build` in `frontend-jsx/` **fails by
   design**: `prebuild` runs `scripts/check-legal.cjs`, which blocks the build
   while `src/legal/privacy.js` still holds three placeholders (the CIN, the
   registered office address with PIN, and the named Grievance Officer required
   under IT Rules 2011 Rule 5(9)). Fill those in and the gate passes.
   `npx vite build` succeeds today because it skips `prebuild`, which is useful
   for checking the build but is not how you ship a page that is missing its
   legal disclosures.
5. Submit the sitemap in Google Search Console.

## Maintenance notes

**Stale files are never removed.** The build writes, it does not clean. If a
letter drops below its threshold, its page leaves the sitemap and stays on
disk, still reachable and still indexable. If you change a URL convention, the
old files remain. Delete them deliberately, and remember there is no version
control to recover them from.

**The stylesheet exists twice.** `shell.ts` exports `PAGE_CSS`, and its own
header comment says `name-page.ts` imports it. It does not.
`backend/src/pdf/name-page.ts` carries its own inline copy of the same block,
in two places (the name page and the `/n/` index). Verified by grep: nothing
outside `shell.ts` references `PAGE_CSS`. A visual change therefore has to be
made in both files or the 537 name pages and the 160 cluster pages drift into
looking like two different sites.

**The palette is locked.** `--accent #B8501C` measures 3.98:1 against the cream
page, under the 4.5:1 AA floor. The founder has decided it stays. This is a
recorded accepted exception, not an oversight. Do not raise it again.

**Adding names is a database edit, not a code edit.** The corpus moved to
`corpus_names`, editable in the founder console. `name-corpus.ts` is now only
the fallback. `docs/SEO_PLAYBOOK.md` still says to edit
`name-corpus.ts` to add names; that instruction is out of date and applies to
the fallback list alone.

**Do not run these commands casually.** `build:names` touches 697 files and
rewrites the sitemap every time. It is a deploy step, not a dev-loop command.
Running the frontend with `npm run dev` serves whatever is already in
`public/`, so there is no reason to rebuild the pages while working on the app.
